# Flames of War V4 rules audit: current implementation

## Scope and source standard

This document audits the behavior present in `app.py`; it does not prescribe changes. The source checked for V4 rules is Battlefront Miniatures Ltd., *Flames of War Quick Reference Sheet* (official Flames of War website, `Documents/Version4/QuickReferenceSheet.pdf`), especially the cited page references below. It is the Flames of War V4 quick reference (the document itself labels rules by V4 rulebook page, is hosted in Battlefront's Version4 directory, and carries Battlefront's 2017 copyright). No V2, V3, Team Yankee, or other game's material was used as a rules source.

Source: [Battlefront's Flames of War V4 Quick Reference Sheet (PDF)](https://www.flamesofwar.com/Portals/0/Documents/Version4/QuickReferenceSheet.pdf).

The quick reference confirms only the rules expressly summarized in it. Where the implementation's generic model cannot be established from that source as a complete V4 rule, the status is `PROJECT_ASSUMPTION` or `UNRESOLVED`; no unstated rule is inferred.

## Findings by topic

| Topic / assumption represented | What `app.py` does | Classification | V4 comparison and basis |
|---|---|---|---|
| Basic To Hit die probabilities | `to_prob()` maps 2+ to 5/6, 3+ to 4/6, …, 6+ to 1/6, and samples that probability with a binomial distribution. | `VERIFIED_V4` | The V4 reference says to roll the target team's “Is Hit On” number (p. 56); this is the corresponding probability for one unmodified six-sided die. The model is valid only as a probability conversion for a fixed target number without modifiers. |
| Modifiers and eligibility for a To Hit number | The UI asks for one To Hit value and applies no range, concealment, Gone to Ground, smoke, night, or out-of-command modifiers; it also omits target selection and hit assignment. | `IMPLEMENTATION_CONFLICT` | V4 To Hit can be modified (Quick Reference, “Score to Hit,” p. 56). The implementation represents a fixed, unmodified target roll rather than the full V4 shooting procedure. Which modifiers apply depends on table state and is outside the app's inputs. |
| 7+ To Hit | For each shot it rolls a first D6 and, only on 6, accepts a second D6 result of 5+. | `VERIFIED_V4` | The V4 reference explicitly states: if 7+ is needed, roll 6 followed by 5+ (“7+ or More to Hit,” p. 56). Its probability is `(1/6)(2/6) = 1/18`. The two arrays may contain unused second rolls for first-roll misses; the boolean condition ensures they cannot become hits. |
| 8+ To Hit | For each shot it rolls a first D6 and, only on 6, accepts a second D6 result of 6+. | `VERIFIED_V4` | The V4 reference explicitly states: if 8+ is needed, roll 6 followed by 6 (“7+ or More to Hit,” p. 56). Its probability is `(1/6)(1/6) = 1/36`. |
| 1+ To Hit entry in helper | `to_prob()` contains a 1+ → 1.0 mapping, but the UI does not offer 1+. | `UNRESOLVED` | The audited V4 quick-reference section specifies the “Is Hit On” roll and special 7+/8+ procedure, but does not establish a general 1+ target rule for this calculator's abstraction. The helper entry is not reachable through the current UI and should not be treated as a verified selectable V4 rule. |
| Shot count as a user-entered number | User selects 1–50 shots; all are independent and share the selected hit target. | `PROJECT_ASSUMPTION` | V4 specifies how many dice to roll from a weapon's ROF: one die per point of ROF, using Halted ROF if not moved and not Pinned Down, otherwise Moving ROF (Quick Reference, “How Many Dice,” p. 56). The app's arbitrary shot count is a convenient scenario input, not a complete representation of weapon ROF, movement, pinning, number/type of weapons, or target assignment. |
| Save threshold as a freely selectable generic stat | The UI permits save values 1+ through 7+ for every notional target, and computes failure as `1 - to_prob(save)`. | `IMPLEMENTATION_CONFLICT` | V4 distinguishes save procedures by target: the target player rolls and adds armour rating and possibly a range modifier against Anti-tank for armour saves (p. 59); “Other Saves” require scoring the save or the team is destroyed, with a Firepower test in specified cases such as Bulletproof Cover (p. 62). A single generic save target applied to every hit is not the V4 save procedure. The UI note that 7+ cannot be saved is arithmetic within this generic model, not a universal V4 save rule. |
| Firepower as a generic kill probability after every failed save | For each failed save, `app.py` makes an independent Firepower-threshold D6 roll; a success counts as one kill. | `IMPLEMENTATION_CONFLICT` | In V4, ordinary infantry/gun/other saves and armour saves resolve differently. The quick reference says ordinary “Other Saves” fail into destruction except specified Firepower-tested cases (p. 62); armour results depend on Anti-tank versus modified armour, and Firepower is used for equal/penetrating armour outcomes (p. 59). Thus a universal save → Firepower → kill chain is not the general V4 resolution sequence. Firepower ratings are weapon attributes; the code treats them as an unconditional kill chance after its generic save. |
| Numeric Firepower probability conversion | `to_prob()` maps 1+–6+ to the chance of rolling that threshold on one D6. | `PROJECT_ASSUMPTION` | V4 uses a weapon's Firepower rating for specified tests; the quick reference identifies when to take those tests (pp. 59, 62), but the generic conversion does not by itself capture the different consequences or triggering conditions. Do not interpret every hit as requiring this roll. |
| Pinning at five or eight hits | The UI reports chance of at least five hits and at least eight hits; labels these “infantry platoon” and “big infantry platoon.” | `PROJECT_ASSUMPTION` | V4's “Pinned Down” summary says a Unit is Pinned Down on a total of 5 hits, or 8 if it has at least 12 Teams; Armoured Tank Teams and Aircraft cannot be Pinned Down (Quick Reference, p. 64). The thresholds align arithmetically, but the code neither takes Unit composition/type nor tests the 12-Team condition, and “big infantry platoon” is not the rule's stated condition. The probabilities correspond to pinning only if all modeled hits count toward one eligible Unit in the relevant shooting step. |
| Meaning and accumulation window for hit thresholds | The simulation treats the generated hits as one pool and sums the histogram tail at 5 and 8. | `UNRESOLVED` | The quick reference states a total-hit threshold for a Unit (p. 64), but this app supplies no Unit identity, team count, eligibility, or turn/step context. It therefore cannot establish that the sampled shot pool is the complete set of hits that should be counted for any particular V4 pinning decision. Verify the intended scenario semantics before describing these percentages as actual in-game pin probabilities. |
| “2+ kills” and “5+ kills” thresholds | The app reports histogram tails for at least two and at least five kills. | `PROJECT_ASSUMPTION` | These are calculator-selected summary statistics. The cited V4 shooting rules do not establish 2 or 5 kills as special game-rule thresholds. |

## Mathematical interpretation of the represented chain

For a selected normal hit target `h` in 2+…6+, the per-shot hit probability is `p_h = (7 - h)/6`. For the implemented special targets, `p_7 = 1/18` and `p_8 = 1/36`. Given user-selected generic save target `s` and firepower target `f`, the code uses `p_fail_save = 1 - p_s` and `p_firepower = p_f`. Its implied per-shot kill probability is `p_h * p_fail_save * p_f` (with the corresponding 7+/8+ hit probability), and it draws kills conditionally from failed saves after drawing hits.

The resulting hits, failed saves, and kills are Monte Carlo samples, not exact outcome distributions. The app runs 50,000 unseeded trials. This describes the implementation's math only; it does not validate the generic save/firepower chain as V4 combat resolution.

## Explicitly unresolved / verification required

1. Whether the desired calculator is intended to model one weapon/one target Unit or an abstract volley across multiple target Units; that determines what a shot count and the pinning hit pool mean.
2. How the user-provided “save” is intended to map to the V4 target categories and armour/Anti-tank comparison. The current generic selector cannot supply this information.
3. Whether a generic Firepower roll is intended only for bulletproof-cover or armour outcomes, or for another explicitly defined project abstraction. The current code applies it to every failed save.
4. Whether the labels “infantry platoon” and “big infantry platoon” are intended to stand for eligible V4 Units of fewer than 12 Teams versus Units with at least 12 Teams. The official summary uses Unit/team-count conditions, not these labels.
5. Any exceptional weapons, special rules, or target states: the UI has no inputs to represent them, so this audit makes no ruling on their effects.

## Recommended next investigation

Have the project owner define the intended scenario abstraction, and consult the V4 rulebook sections on Shooting (especially “Score to Hit,” “How Many Dice,” “Roll Armour Saves,” “Other Saves,” and “Pinned Down,” pp. 56, 59, 62, 64 in the cited quick reference) for the full surrounding procedures. Resolve target class, team count, ROF/state, and hit-pool scope in a written specification before treating generic save/firepower calculations or threshold labels as V4 rules.
